Shared DNS safety boundary

The parent hosted zone is never a managed resource in this stack.

Pulumi will call aws.route53.get_zone as a read-only data lookup. The stack will not declare, import, adopt, protect, update, or delete an aws.route53.Zone for wdwebsolutions.com.

The stack must read the parent zone ID to create the demo's A and AAAA alias records. Those two records are owned by this stack and are removed by pulumi destroy. The shared parent zone and unrelated records are untouched.

Automated infrastructure tests will reject any accidental route53.Zone declaration, and every preview must pass the expected-account and hosted-zone containment checks.

One-time setup

Phase 1

Implement and verify application artifacts

  1. Keep services, gallery, and resources/articles on their existing seeded frontend data.
  2. Add dependency-injected demo and HTTP adapters for contact submission.
  3. Add disabled database and SES configuration paths and tests.
  4. Build and test everything locally.
python3 scripts/project.py setup
python3 scripts/project.py test
python3 scripts/project.py build
Phase 2

Initialize the operator-run Pulumi stack

Pulumi Cloud stores both stacks. The shared foundation stack owns only account-global GitHub OIDC configuration; the disposable demo stack owns the application. Pulumi remains outside application CI/CD.

cd infra/foundation
pulumi stack init shared
pulumi preview --diff --stack shared
pulumi up --stack shared

cd ..
pulumi stack init demo
pulumi preview --diff --stack demo
pulumi up --stack demo
Phase 3

Review the first preview

python3 ../scripts/package_lambda.py
pulumi preview --diff --stack demo

The preview must show no hosted-zone creation, import, replacement, or deletion. It should show only the demo DNS records in the shared zone.

Phase 4

Create the AWS resources

pulumi up --stack demo

The shared stack creates the account-global GitHub OIDC provider. The demo stack creates the application, least-privilege deploy role, tagged resources, and budget. Pulumi exports the deployment identifiers:

  • githubDeployRoleArn
  • frontendBucketName
  • cloudFrontDistributionId
  • lambdaFunctionName
  • demoUrl
Phase 5

Enable cost allocation and create the client budget

Every taggable resource receives client_name=austinsurfacepros, env=demo, demo=true, and a unique billing_scope=austinsurfacepros-demo.

The $5 budget already exists and filters on user:billing_scope$austinsurfacepros-demo. AWS can take up to 24 hours to expose a new user-defined tag for activation and another 24 hours to activate it. Cost matching is therefore staged:

  1. The first app pulumi up created and tagged the resources and budget.
  2. After billing_scope becomes available, set the foundation config flag and let Pulumi activate it.
  3. The existing budget begins matching tagged costs after AWS reports the tag as active.
cd infra/foundation
pulumi config set activateCostAllocationTags true
pulumi up --stack shared

The budget filters on user:billing_scope$austinsurfacepros-demo, has a monthly limit of $5, and emails the configured address at forecasted 80%, actual 80%, and actual 100% thresholds.

AWS Budgets sends subscriber emails directly. SES verification is not involved in budget notifications; the existing SES identity remains useful for the future contact notifier.

Phase 6

Use the GitHub demo environment

The workflow references environment: demo, so GitHub creates the environment automatically on its first run. The six deployment identifiers are non-secret and are versioned in the workflow; no GitHub secret or long-lived AWS key is required.

Phase 7

Create the deployment workflow and branch

The trusted workflow uses two jobs. The validation/build job runs proposed PR code with only contents: read. The deployment job receives the tested artifacts and alone requests id-token: write. The AWS role can only write to the demo bucket, update the demo Lambda, and invalidate the demo CloudFront distribution.

on:
  push:
    branches: [demo]
  pull_request_target:
    branches: [demo]

concurrency:
  group: austinsurfacepros-demo-deployment
  cancel-in-progress: true

Internal PRs may deploy to the shared preview. Fork PRs are excluded from publishing. Closing a PR restores the current demo branch deployment.

Phase 8

Exercise the complete path

  1. Create demo from the reviewed baseline.
  2. Open an internal test PR targeting demo.
  3. Confirm build, test, OIDC assumption, S3 sync, Lambda update, invalidation, and smoke test.
  4. Close the PR without merging and confirm the workflow restores the branch version.
  5. Merge a second PR and confirm the push deployment is authoritative.

Teardown

cd infra
pulumi destroy --stack demo

The demo records and application resources are removed. The shared wdwebsolutions.com hosted zone and wildcard certificate remain untouched.
